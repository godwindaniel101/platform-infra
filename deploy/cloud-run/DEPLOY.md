# The Pact Broker on Cloud Run

The broker is a stateless HTTP container with a Postgres database behind it.
Cloud Run fits that exactly:

- it scales to zero between builds, so it costs almost nothing while idle
- it gets a public HTTPS address, which a GitHub runner can reach with no
  tunnel and no self-hosted runner
- the only stateful part is Cloud SQL, which takes the backups

## Before you start

```bash
brew install --cask google-cloud-sdk    # if gcloud is not installed
gcloud auth login
gcloud config set project <your-project-id>
```

## Deploy

```bash
export GCP_PROJECT=<your-project-id>
export GCP_REGION=europe-west1          # or africa-south1, or wherever you run
./deploy.sh
```

The first run takes about ten minutes, nearly all of it waiting for Cloud SQL.
Run it again whenever you want to change something: every step checks first, so
a second run is safe.

## What it creates

| Thing | Name | Note |
|-------|------|------|
| Cloud Run service | `pact-broker` | public HTTPS, scales to zero |
| Cloud SQL instance | `pact-broker-db` | Postgres 16, `db-f1-micro`, daily backup at 02:00 |
| Database | `pact_broker` | |
| Secret | `pact-broker-db-password` | generated, never printed |
| Secret | `pact-broker-basic-auth-password` | generated, printed once at the end |

## Cost

Roughly **10 to 15 US dollars each month**, nearly all of it the Cloud SQL
instance. Cloud Run itself is close to nothing: a broker is read a few times per
build and sleeps between them.

For comparison, the PactFlow Team plan is 127 dollars each month and caps at 50
integrations. The saving grows with every service you add.

## The security decisions, and why

**Read is authenticated.** `PACT_BROKER_ALLOW_PUBLIC_READ` is `false`. The local
`docker-compose.yml` sets it to `true` for convenience, and that is fine on a
laptop. On a public address it is not: a contract states the shape of an
internal payment API, field by field.

**The heartbeat is public.** `PACT_BROKER_PUBLIC_HEARTBEAT=true` keeps
`/diagnostic/status/heartbeat` open with no credentials, so Cloud Run and the
wait scripts can check health without holding a password.

**Cloud Run allows unauthenticated requests, and the broker does its own auth.**
This looks wrong at first. The reason is that Cloud Run IAM and the broker both
want the `Authorization` header: IAM wants `Bearer <token>`, the broker wants
`Basic <credentials>`, and a request has only one such header. Turning IAM on
would make every pact tool fail with 401 and no clear cause.

If you need more than a password, the next step is Cloud Armor on the service
with an allow list, not Cloud Run IAM.

**Both passwords are generated by the script** and go straight into Secret
Manager. The database password is never printed at all. A password in a
scrollback buffer is a password you have to rotate.

## Cold start

With `--min-instances=0` the first request after an idle period waits a few
seconds while the container starts. That is fine for a build.

If a cold start ever makes a pipeline flaky, set:

```bash
BROKER_MIN_INSTANCES=1 ./deploy.sh
```

That keeps one instance warm and adds a few dollars each month.

## After the deploy

The script prints the exact commands. In short:

1. Put `PACT_BROKER_BASE_URL`, `PACT_BROKER_USERNAME` and
   `PACT_BROKER_PASSWORD` into both service repositories as secrets. The gate in
   `ci/contract-gate.sh` skips itself with a warning until they exist, so the
   pipeline is green but it is not guarding anything.
2. Run `scripts/create-webhooks.mjs` with `CI_PLATFORM=github`. Until the
   webhook exists a consumer change does not start the provider build, and
   `can-i-deploy` answers "unknown". **Unknown is not a pass.**

## Check it worked

```bash
curl -fsS "$PACT_BROKER_BASE_URL/diagnostic/status/heartbeat"      # public
curl -fsS -u "$PACT_BROKER_USERNAME:$PACT_BROKER_PASSWORD" \
  "$PACT_BROKER_BASE_URL/pacticipants"                             # authenticated
```

The second one must fail without the credentials. If it succeeds without them,
public read is still on and anyone can read your contracts.

## Backups and restore

Cloud SQL takes a daily backup at 02:00. To list and restore:

```bash
gcloud sql backups list --instance=pact-broker-db
gcloud sql backups restore <backup-id> --restore-instance=pact-broker-db
```

Losing the broker database is not an emergency: every contract can be published
again from the consumer builds. What you lose is the deployment history, and
`can-i-deploy --to-environment production` stops knowing what production runs
until each service records its deployment again.
